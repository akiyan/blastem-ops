# サウンド CPU（Z80）の観測

停止中に Z80 のレジスタ・状態・RAM を読み、フレームごとに Z80 が実行した・止められたサイクル数を記録する。サウンドドライバの処理落ちやバス要求の影響を、録音から推測せずに数値で確認できる。

## MCP: `z80_state`

停止中（フレーム制御または GDB による停止）に呼ぶ。

| 入力 | 内容 |
|---|---|
| `address` | 省略可。読む Z80 RAM の先頭（0〜1FFF） |
| `size` | `address` と併用。1〜256 バイト、既定 16 |

応答:

- `state`: SP、A、F、BC、DE、HL、IX、IY、I、割り込みモード、IFF1/IFF2、68000 側のバンクレジスタ（Z80 の 8000〜FFFF の窓）、`reset`・`busreq`・`busack`
- `state.last_frame`: 直前に完了したフレームで、Z80 が実行したサイクル数（`run`）、68000 のバス要求で止められたサイクル数（`busack`）、リセットで止まっていたサイクル数（`reset`）。NTSC では合計が1フレーム約 59,700 サイクル
- `state.total`: 起動からの累計
- `ram`: 指定した範囲の hex

PC は返さない。JIT は同期点の間 Z80 の PC を更新しないため、最新の値を保証できない。

## フレームごとの記録

[フレームごとの値の記録](frame-trace.md) の `space` に `z80_ram`（Z80 RAM）と `z80_frame` を指定できる。`z80_frame` は `size` 4 で、`address` 0 が実行、1 がバス要求による停止、2 がリセット中の、直前のフレームのサイクル数。

```json
{"frames": 120, "watches": [
  {"name": "run", "space": "z80_frame", "address": 0, "size": 4},
  {"name": "busack", "space": "z80_frame", "address": 1, "size": 4},
  {"name": "counter", "space": "z80_ram", "address": 4096}
]}
```

実際の XGM2 ドライバを使う ROM では、1フレームあたり実行約 59,200、バス要求による停止約 500 サイクルだった。

## 本体: v2 `z80_state`・`z80_read`

capability は `z80_observation`。`z80_state` は params なし、`z80_read` は `address`・`size`（`ram_read` と同じ応答形式）。サイクル数は Z80 の実行関数で、実行・バス要求による停止・リセットの区間をマスタークロックで積算し、Z80 のクロック分周で割って返す。

## 制限

- 新しい CPU コア（`NEW_CORE` ビルド）では使えない
- バス要求の停止サイクルは、BlastEM のバス受け渡しの近似（M サイクル単位）に従う

## 試験

fixture は起動時に Z80 RAM へ「0x1000 番地を増やし続けるループ」を書いて Z80 を動かす。B を押している間は 68000 が Z80 のバスを要求し続ける。

- Z80 RAM にプログラムが読め、カウンターがフレームごとに変わる
- B なしでは1フレームの実行サイクル数が 59,000〜60,500 で、停止は 0
- B ありでは実行が 1,000 未満、バス要求による停止が 58,000 を超え、カウンターが止まる
- 範囲外・幅の不正な読み出し、実行中の要求を拒否する
